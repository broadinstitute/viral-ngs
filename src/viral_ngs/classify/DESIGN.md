# Classifier Design Notes

This document captures architecture, data contracts, and design decisions for
classifier wrappers and post-processing helpers under `viral_ngs.classify`.

The intent is to preserve why each component behaves the way it does, not just
what the code currently does. Add a new section for each classifier as behavior
becomes non-obvious or pipeline-facing contracts are established.

## VirNucPro

VirNucPro support in viral-ngs is post-processing around VirNucPro outputs. The
model/tool execution itself is not implemented here. The relevant helpers are:

- `classify_contigs()`: converts VirNucPro highest-score chunk output into one
  call per assembled contig.
- `classify_reads_by_contig()`: labels reads using a minimap2 BAM aligned to
  contigs plus the per-contig calls from `classify_contigs()`.
- `metagenomics.py virnucpro_contigs` and
  `metagenomics.py virnucpro_label_reads_by_contig`: CLI entry points for those
  helpers.

### Contig Classification

VirNucPro emits predictions at chunk/sequence granularity. The wrapper groups
rows back to contigs by extracting an ID from the configured ID column. By
default, IDs are grouped with `r"(NODE\_\d+)"`, while the output contig ID is
the input ID with a trailing `_chunk_<n>` suffix removed. For example,
`NODE_10_length_100_chunk_1` groups under `NODE_10` but is emitted as
`NODE_10_length_100`.

Each chunk contributes a signed score delta:

```text
delta = max_score_1 - max_score_0
```

The contig-level `weighted_delta` weights chunks by `sqrt(abs(delta))`. This
gives stronger influence to chunks with clearer model separation while still
allowing weaker chunks to contribute. If all weights are zero, the code falls
back to a plain mean so the result remains defined.

The contig-level call logic is intentionally threshold-driven:

- Positive weighted deltas strictly above `min_weighted_delta` call `Viral`.
- Negative weighted deltas strictly below `-min_weighted_delta` call
  `Non-viral`.
- Deltas inside that band, including exact threshold-boundary values, call
  `Ambiguous`.
- Confident chunks also use strict boundaries: the winning score must be greater
  than `min_confident_score`, and the opposing score must be less than
  `max_opposing_score`.
- High/moderate/low-confidence tiers require both a strong weighted delta and
  enough confident chunks of the winning class.
- Ambiguous chunks are excluded from the denominator used for viral/non-viral
  confident chunk proportions.
- Contigs with too few chunks are demoted because a strong delta from limited
  evidence should not be reported as high/moderate confidence:
  `high_confidence`/`moderate_confidence` becomes `low_confidence`, while
  `low_confidence` becomes `review`.

Empty VirNucPro input is treated as a valid no-call result and writes a
header-only contig classification table. Missing required columns or wholly
unmatched IDs are treated as configuration/input-shape errors and raise.

Rows whose IDs do not match `id_pattern` are excluded with a warning when at
least one other row matches. If no rows match, the input shape is treated as
invalid and the helper raises.

The emitted contig table rounds `weighted_delta`, `viral_proportion`, and
`nonviral_proportion` to three decimals and naturally sorts rows by contig ID.

### Read Labeling Input Contract

Read labeling consumes a minimap2-produced BAM, not PAF. PAF was an interim
format; the durable pipeline artifact is the BAM generated by the minimap2
alignment path.

Required BAM assumptions:

- Records are aligned to the same contig IDs used in the contig classification
  table.
- Mapped primary records include `NM:i`, which minimap2 SAM/BAM output provides
  in the pipeline path.
- Input record order is used as the final deterministic tie-breaker. Avoid
  re-sorting or otherwise reordering the BAM between minimap2 alignment and
  read classification if exact tie reproducibility matters.

Unmapped records are ignored before validation, so missing `NM:i` on unmapped
records is harmless. Missing `NM:i` on any retained mapped primary record is
fatal. Other SAM flags, including duplicate and QC-fail, are not special-cased;
mapped primary records with those flags are processed.

Unmapped records do not produce output rows. Secondary and supplementary records
are counted for logging but skipped before DuckDB ingestion. This preserves the
intended behavior of labeling reads from primary alignments only and avoids
inflating multi-mapping signals with alternate/split alignment records.

### BAM Metric Derivation

The read-labeling path normalizes primary BAM alignments into a compact
temporary TSV before DuckDB processing. The TSV stores the alignment context
needed by the output and ranking logic:

- read and contig IDs
- read and contig lengths
- query/reference alignment spans
- strand
- mapping quality
- percent identity
- percent query coverage
- original source order

Percent identity and query coverage are derived from BAM fields rather than
stored directly in BAM:

```text
alignment_block_length = sum(CIGAR ops M, I, D, =, X)
num_matches = alignment_block_length - NM
pct_identity = 100 * num_matches / alignment_block_length
pct_query_cov = 100 * aligned_query_bases / query_length
```

Soft clips contribute to total query length but not aligned query bases. Indels
are included in the identity denominator so deletion/insertion-heavy alignments
are not over-scored. This is intentionally gap-inclusive, PAF-column-11-style
identity, not minimap2's gap-compressed `de:f` divergence tag.

`min_identity` and `min_query_cov` thresholds are percent values on a `0..100`
scale. Fractional values such as `0.9` are rejected because the old PAF path
accepted fractional-scale inputs in some cases; silently treating `0.9` as
`0.9%` would make the filter effectively useless.

### Read Labeling Decision Logic

The read label is computed in DuckDB for scalability. The flow is:

1. Load normalized primary alignments.
2. Compute `mapped_well` from mapping quality, percent identity, and percent
   query coverage.
3. Load per-contig VirNucPro classifications.
4. Left-join alignments to contig calls on `target_name = ID`.
5. Fill missing contig calls with `Unclassified`.
6. Count distinct calls across all retained primary alignments for each read.
7. Pick the best alignment per read by:

```text
mapping_quality DESC, pct_identity DESC, source_order ASC
```

8. Emit `Multi-mapped` if a read has retained primary alignments to contigs
   with more than one distinct call. Otherwise emit the selected alignment's
   call.

This means `mapped_well` is a quality annotation, not a row-retention filter and
not the deciding factor for `Unclassified`. A read can be labeled
`Unclassified` even when `mapped_well` is true if its selected contig is absent
from the contig classification table.

`Multi-mapped` is computed across all retained primary alignments, including
alignments where `mapped_well` is false. A low-quality alignment to a contig with
a different call can therefore still make the read `Multi-mapped`; the quality
assessment remains visible in the separate `mapped_well` column.

The selected alignment is deterministic for a fixed BAM order, but the output TSV
does not explicitly sort result rows. Downstream consumers that diff or compare
whole files should sort by `read_id` if row order matters.

### `Unclassified` Semantics

`Unclassified` is assigned when a retained primary read alignment maps to a
contig that has no matching row in the per-contig VirNucPro classification TSV.

Consequences:

- Reads with no retained primary alignments produce no output row.
- Reads mapping only to missing/unclassified contigs are emitted as
  `Unclassified`.
- Reads mapping to both classified and missing/unclassified contigs are emitted
  as `Multi-mapped`, because their retained alignments span multiple distinct
  calls.
- `Unclassified` does not mean the read failed alignment quality thresholds; the
  `mapped_well` column carries that separate quality assessment.

### Resource Management

DuckDB is used because read-by-contig labeling can involve many alignment rows
and a large join against contig calls. Intermediate alignment/classification
tables spill under a per-run temporary directory.

The temporary TSV is a deliberate simple interchange format: it avoids holding
all BAM-derived rows in Python memory and keeps DuckDB ingestion independent of
pysam objects. It is not a durable artifact or API; a future Arrow or batched
DuckDB registration path could replace it if profiling shows the TSV
write/read/parse cycle is material.

If no DuckDB memory limit is supplied, the helper reads cgroup memory limits and
caps DuckDB to roughly 75% of the available memory. The remaining memory is left
for Python, pandas dataframes, file buffers, and page cache. Passing an empty
string explicitly disables this cap.

### Non-goals

These helpers do not run VirNucPro, run minimap2, filter reads out based on
`mapped_well`, rescue missing contig classifications, interpret taxonomy, or
collapse duplicate read names beyond selecting one best retained primary
alignment row for output.

### Design Decisions

| Decision | Rationale |
| --- | --- |
| BAM is the read-labeling input, not PAF. | The pipeline already produces a minimap2 BAM as the durable artifact. Keeping PAF would preserve temporary glue and duplicate alignment contracts. |
| Require `NM:i` on retained mapped primary records. | Identity filtering depends on edit distance. The pipeline minimap2 path provides `NM`, so missing `NM` indicates an invalid input for this helper. |
| Reject fractional identity/query-coverage thresholds. | BAM-derived metrics are emitted on a `0..100` percent scale. Rejecting values like `0.9` avoids silently weakening the filter after the old PAF compatibility path was removed. |
| Skip secondary/supplementary records before DuckDB. | The output labels reads from primary alignments. Filtering early avoids spilling rows that would always be discarded and prevents alternate/split records from inflating multi-map calls. |
| Include indels in identity denominator. | This follows alignment-block semantics and prevents insertion/deletion-heavy alignments from appearing artificially high identity. |
| Use `source_order` as final tie-breaker. | Deterministic alignment selection is required when mapping quality and identity tie. Source order gives stable behavior as long as callers do not reorder the BAM. |
| Left-join contig calls and coalesce missing calls to `Unclassified`. | Missing contig calls are informative and should be surfaced per read instead of dropping the read silently. |
| Mark mixed-call reads as `Multi-mapped`. | If retained primary alignments connect a read to contigs with different biological calls, reporting a single selected call would hide ambiguity. This intentionally considers low-quality retained alignments too; `mapped_well` remains separate context. |
| Keep `mapped_well` separate from call assignment. | Alignment quality is useful context, but low-quality mapped reads should still be visible to downstream review rather than silently removed. |
| Treat the normalized alignment TSV as an implementation detail. | The TSV keeps ingestion simple and memory-bounded today, but it is not a pipeline contract and can be replaced by a typed/batched DuckDB ingestion path. |

## Kallisto

Kallisto support in viral-ngs is implemented as a `kallisto` wrapper around the
`kb-python` CLI. The public viral-ngs command names use `kallisto`, but the
actual execution backend remains `kb count`, `kb extract`, and `kb ref`.

This split is intentional: downstream pipelines think in terms of Kallisto, but
the actual implementation we rely on is the `kb-python` orchestration layer over
`kallisto` and `bustools`.

### Count/Extract Pipeline Contract

The supported first-party flow is:

1. `metagenomics kallisto_build` builds the index (`kb ref`) that every count
   and extract call consumes. It is setup rather than per-sample
   classification, but the count/extract contract below silently assumes its
   output exists.
2. `metagenomics kallisto` runs count and emits:
   - `adata.h5ad`
   - `counts.tsv`
3. `metagenomics kallisto_extract` consumes:
   - explicit `--targets`, or
   - `--h5ad` from the prior count output in order to derive target IDs

   and emits `summary.tsv` plus `read_hits.tsv`.
4. `metagenomics kallisto_top_taxa` consumes:
   - `counts.tsv`

Tarball-based count outputs are no longer part of the supported contract.

### Public vs Internal Outputs

The public pipeline-facing outputs are TSV-first:

- `counts.tsv`: long-form count table with columns `sample_id`, `db_hit_id`,
  and `count`
- `summary.tsv`: read-level extract summary with columns `SAMPLE_ID`,
  `READ_ID`, `DB_ID`, `TAXONOMY_LINEAGE`, `TAXONOMY_NAME`, and
  `SEQUENCE_LENGTH`

The extract step also writes `read_hits.tsv` (columns `read_id`, `db_hit_id`)
into the same output directory. It is a secondary read-to-hit table, not the
primary reporting surface; `summary.tsv` is the human-readable extract output.
Consumers should not assume `summary.tsv` is the only file extract writes.

`adata.h5ad` is still emitted by the count step because the viral-ngs
`kallisto_extract` derive-targets path consumes it (via
`extract_hit_ids_from_h5ad`) when `--targets` is omitted. The `kb extract`
backend itself takes explicit target IDs (`-ts`) and does not read the H5AD, so
the dependency lives in the viral-ngs orchestration, not the backend. The H5AD
remains a durable workflow artifact, but it is not the preferred human-readable
reporting format.

### `kallisto_extract` Target Selection Contract

`metagenomics kallisto_extract` supports two target-selection modes:

- `--targets`: comma-separated raw DB hit IDs to extract
- `--h5ad`: path to the exposed `adata.h5ad` generated by a prior
  `metagenomics kallisto` count run

When `--targets` is provided, those IDs are used directly and `--threshold` is
ignored.

When `--targets` is omitted, `--h5ad` is required. In that mode, the command
parses the H5AD, sums counts across the single sample represented in that file,
and extracts every hit ID with count `>= --threshold`.

Important constraints:

- The H5AD path is expected to come from the viral-ngs/viral-pipelines Kallisto
  count step, not from an arbitrary matrix-producing tool.
- This extraction mode requires a single-sample H5AD and raises if the H5AD has
  more than one observation. That matches the current pipeline contract, where
  each invocation processes one sample at a time.
- The extracted IDs are raw DB hit IDs from the Kallisto result. They are not
  translated through the `t2g` file at this stage.
- If the H5AD contains no hits at or above threshold, extract writes header-only
  `read_hits.tsv` and `summary.tsv` rather than treating the sample as an error.

### Taxonomy Map Contract

`--id-to-tax-map` is optional post-processing metadata for `summary.tsv` and
top-taxa reporting. It is not used to determine which hits are counted or
extracted.

Accepted mapping shapes are intentionally flexible because existing upstream
reference metadata generated alongside Kallisto/PalmDB-style databases has not
always used one exact schema. In viral-pipelines, this file is supplied as the
taxonomy metadata paired with the Kallisto database, not produced by
`kallisto_extract` itself.

- CSV or TSV
- headered or headerless
- rows beginning with a DB hit ID followed by taxonomy lineage columns
- optional duplicate ID columns
- optional trailing strand/genome-type columns such as `+ssRNA` or `-ssRNA`

Headered CSV example:

```text
palmDB_ID,palmDB_ID,tax_level_1,tax_level_2,tax_level_3,strand
u104347,u104347,Viruses,Pisuviricota,Nidovirales,-ssRNA
```

Headerless CSV example:

```text
u104347,Viruses,u1,Pisuviricota,Pisoniviricetes,Nidovirales,Coronaviridae,-ssRNA
```

Parser semantics:

- Column 1 is always the DB hit ID used in `counts.tsv` and `summary.tsv`.
- If column 2 duplicates column 1, column 2 is treated as duplicate ID metadata
  and skipped before taxonomy parsing.
- Taxonomy lineage values are read from the remaining taxonomy columns.
- Empty values and literal `.` placeholders are ignored.
- Trailing strand/genome-type values such as `+ssRNA`, `-ssRNA`, `dsRNA`,
  `+ssDNA`, or `-ssDNA` are metadata and are stripped from the reported lineage.

The parser normalizes those variants so the downstream Kallisto reporting code
can stay tolerant of existing reference metadata without forcing a single new
taxonomy-map producer first.

#### Unclassified fallback

The taxonomy fallback is palmDB/RdRP-oriented, reflecting the current reference
domain. When a taxonomy map is provided but a hit ID is missing from it, or its
taxonomy columns are empty, the reported lineage and name are both the literal
`Unclassified RdRP`. This sentinel surfaces in `summary.tsv` and the top-taxa
report. When no taxonomy map is provided at all, the taxonomy fields are left
empty instead.

#### Reported taxonomy level

`TAXONOMY_NAME` is not uniform across commands. It is selected from the lineage
by a `highest`/`deepest` level:

- `kallisto_extract` (`summary.tsv`) reports the `highest` (broadest) lineage
  element by default.
- `kallisto_top_taxa` reports the `deepest` (most specific) lineage element.

`TAXONOMY_LINEAGE` is always the full `;`-joined lineage regardless of level.

### Missing And Empty Input Contract

Missing input is an error for both BAM and FASTQ paths. `metagenomics kallisto`
and `metagenomics kallisto_extract` raise `FileNotFoundError` before checking
whether the input is FASTQ or BAM.

Existing empty BAM input is treated as a valid no-hit case, not as an execution
failure. This stable-artifact guarantee is driven by the `samtools ... isEmpty`
check after the input path has already been confirmed to exist.

For empty BAM count input, `metagenomics kallisto` writes:

- `adata.h5ad` as a `1 x 0` matrix with the sample metadata populated
- `counts.tsv` as a header-only file

For empty BAM extract input, or for extract target derivation that finds no
targets in the H5AD, `metagenomics kallisto_extract` writes:

- `read_hits.tsv` as a header-only file
- `summary.tsv` as a header-only file

This keeps the output contract stable for WDL/pipeline consumers, which should
not need special-case “no output produced” handling for empty samples.

### Design Decisions

| Decision | Rationale |
| --- | --- |
| Keep `kallisto` as the public wrapper name while still executing `kb-python`. | The downstream pipeline interface should reflect the classifier family, while the implementation continues to use the maintained `kb` orchestration layer. |
| Keep `adata.h5ad` alongside TSV outputs. | The viral-ngs `kallisto_extract` derive-targets path needs the count H5AD when `--targets` is omitted, even though TSV is the preferred public reporting format. The `kb extract` backend itself takes explicit IDs and does not read the H5AD. |
| Use long-form `counts.tsv` rather than a wide matrix. | The current pipeline processes one sample per invocation, so a long-form table is easier to consume consistently and scales better than exposing a mostly one-row wide matrix. |
| Derive extract targets from H5AD only when `--targets` is omitted. | Explicit targets should always win; the H5AD path is a convenience mode for “extract all count-positive hits above threshold” workflows. |
| Keep target IDs as raw DB hit IDs. | Translation through `t2g` is downstream analysis behavior, not part of the Kallisto count/extract contract. |
| Accept multiple taxonomy-map shapes. | Existing upstream reference metadata is not fully standardized; tolerant parsing avoids breaking current inputs while still producing stable downstream annotations. |
| Treat existing empty BAM input as a valid output-producing case. | Downstream workflows expect stable artifacts for empty samples. Missing input is still an error; only real existing empty BAMs produce empty count/extract outputs. |
| Write `read_hits.tsv` alongside `summary.tsv` from extract. | `summary.tsv` is the human-readable surface; `read_hits.tsv` is a minimal read-to-hit table retained as a secondary output for consumers that only need the mapping. |
| Default missing taxonomy to `Unclassified RdRP`. | The current reference domain is palmDB/RdRP. A fixed sentinel keeps `summary.tsv` and top-taxa output well-formed when a hit is absent from the taxonomy map. |
| Report `highest` taxonomy for extract and `deepest` for top-taxa. | Read-level summaries favor a stable broad label, while focal top-taxa reporting wants the most specific name available. |
